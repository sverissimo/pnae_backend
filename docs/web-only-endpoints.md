# Web-only endpoint catalog

These endpoints are not consumed by the frozen mobile app. The compact index lives in [AGENTS.md](../AGENTS.md#endpoints-not-used-by-mobile).

Links to `plans/archive/` are historical implementation background; current guidance must stand independently.

## Dashboard

- GET /relatorios/dashboard — aggregated stats for the web dashboard page (summary gauges, top SREs/tecnicos, by-regional, 30-day line chart). Role-aware via `req.user` only — no query params. Uses dashboard-only regional scoping for the per-user PNAE portion (gauges + 30-day line chart) while always using the full hydrated set for the global tops and by-regional chart. Also returns `manuais30Dias` (`{ total, byDay[30] }`) — count + per-day series of active manual relatórios over the same 30-day window, sourced from the gateway GraphQL `atendimentosManuaisUltimos30Dias` query via `AtendimentoService.getManuaisUltimos30Dias`; admin/developer callers are unscoped, while coordenador-regional and extensionista callers pass only `id_reg_empresa` (regional scope, never user scope). A missing regional for a non-admin degrades to zeros instead of falling back to state-wide, and a gateway failure also degrades to zeros rather than blanking the dashboard. Day-bucketing happens in `buildManuais30Dias` (domain) so `byDay` stays aligned to `lineChart.categories`.

## Approve atendimento

- PATCH /atendimento/:atendimentoId/aprovar — coordenador-regional **or admin**. Lives on `AtendimentoController` (declared above `@Patch(':id')` so the 2-segment path isn't shadowed). Two-step authorization, both on `Usuario`: capability (`isCoordenadorRegional() || isAdmin()`, else **403**) then visibility (`hasAccessTo` on the scope from `AtendimentoService.getAtendimentoAuthScope(atendimentoId)`, else **404** to hide existence). Keyed on `atendimentoId` alone (the external-DB PK), so there is no `relatorioId` and no IDOR-pairing check — auth runs on the resolved scope regardless of the id sent. Forwards to the gateway `PATCH /api/aprovarAtendimento/:id`; empty body; busts the atendimento cache and bumps the manual-list cache version.

## Mark atendimento pending

- PATCH /atendimento/:atendimentoId/pendencia — same authorization and shape as the aprovar route above; forwards to the gateway `PATCH /api/criarPendenciaAtendimento/:id`.

## Approve SEI

- PATCH /atendimento/:atendimentoId/aprovar-sei — **admin-only** DETEC/SEI approval of the relatório. Same `atendimentoId`-keyed shape as the validation routes, but the capability gate is `isAdmin()` alone (else **403**) via `assertCanAprovarSei`, then visibility (`hasAccessTo` on `getAtendimentoAuthScope(atendimentoId)`, else **404**) — a no-op for admins today, kept for model symmetry / a future scoped DETEC perfil. Sets `at_atendimento.data_sei = today()` via gateway `PATCH /api/aprovarSei/:id`; empty body; busts the atendimento cache and bumps the manual-list cache version. The coordenador-validation precondition (`data_validacao` present) is enforced atomically **in the gateway** and surfaces as a **400 with the gateway's message preserved** (the `RestAPI.patchAtendimentoValidacao` helper now reads the gateway `{ error }` body, so the reason reaches the UI via `PlainTextExceptionFilter`).

## Remove SEI approval

- PATCH /atendimento/:atendimentoId/remover-aprovacao-sei — admin-only; same auth shape as aprovar-sei; sets `data_sei = null` via gateway `PATCH /api/removerAprovacaoSei/:id`. No precondition (admins can always undo). Downstream-stage locking (`data_see`/`dt_export_ok`) is client-side UX only in v1 — not server-enforced. Busts the atendimento cache and bumps the manual-list cache version.

## Download atendimento file

- GET /atendimento/getArquivos?atendimentoId=&fileType=foto|relatorio — downloads a stored file for an atendimento (PDF when `fileType=relatorio`, image when `fileType=foto`). Both are query params; the controller validates `fileType` is exactly `foto` or `relatorio`. The REST client maps those semantic values to the **PNAE-supported** `tipo_arquivo` MIME set (`application/pdf` for `relatorio`; `image/jpeg`, `image/png`, `image/gif` for `foto`) before calling `GET /api/getArquivos`, which returns `{ arquivo }` — a text column that actually holds the binary payload. The DOCX/TIFF/`application/msword` probe branches were intentionally dropped: a DB check found the relatório artifact is always a PDF and the proof-of-visit always an image, with only ~3 stray `application/msword` rows treated as bad data (never fetched here). The gateway route `GET /api/getArquivos` lives on the emater server (added for this flow — see its `atendimentoRoutes`): it returns the **lowest-`idArquivo` active** file matching that exact `tipo_arquivo` as `{ arquivo }`, or `{ arquivo: null }` on a miss (a normal 200 that advances the client to the next MIME). So selection is deterministic ("lowest `idArquivo` first") both here and in the list `arquivos[]` metadata. `AtendimentoService.getArquivos` decodes it via [decode-arquivo.ts](../src/modules/atendimento/utils/decode-arquivo.ts) (handles data-URI / `\x` hex bytea / raw base64, with magic-byte Content-Type sniffing so a `foto` resolves to JPEG vs PNG correctly), and the controller streams the bytes back with the detected `Content-Type`. Must sit above `@Get(':id')` in the controller so the static route isn't shadowed. Web-only; the storage encoding is a best-effort guess and may need revisiting if the gateway format differs.

## List manual relatorios

- GET /atendimento/com-relatorio-manual — web-only paginated list of Demeter atendimentos that have a manual relatório, sourced from gateway GraphQL `atendimentosComRelatorioManual`. Query params: optional `pageSize` (default 200, clamped 1..1000) and optional opaque `cursor`. Pushes authenticated `req.user` scope upstream before pagination (admin/developer: no scope; coordenador regional: `id_usuario + id_reg_empresa`; staff: `id_usuario`; missing/unsupported user: 403). Enriches each row with cached município/regional/SRE names from `getMunicipiosEmater` (`nomeMunicipio`, `nomeRegional`, `regionalSre` — the gateway query resolves `regional_sre` via a `ger_municipio_ensino`/`ger_regional_ensino` lateral join), collapses `clientes[0]` / `usuarios[0]` for PNAE's table view, and stays additive to the mobile contract. Each row also carries `arquivos[]` (`{ idArquivo, tipoArquivo, nomeArquivo }`, ordered lowest `idArquivo` first) — file metadata loaded upstream via a batched `at_arquivo` child query after the keyset page ids are known (the `arquivo` binary is never selected there). `tipoArquivo` is the raw stored MIME so the frontend derives its actions without sniffing bytes; `nomeArquivo` is an app-generated presentation name (`foto_<id>` for images, else `relatorio_<id>`), never Demeter's `nome_arquivo`. Rows also carry `dt_export_ok` (additive, projected end-to-end from the gateway) so the web table can evaluate the same SEI-lock UX guard as the regular relatórios table. Responses are served through `CachedDemeterListReader` ([src/modules/atendimento/cache/](../src/modules/atendimento/cache/)): whole-page Redis cache, 90s TTL, key = version + scope (`admin` / `staff:<id>` / `coord:<id>:<reg>`) + pageSize + cursor; the version key is bumped by the four validation mutations above, and externally-created Demeter rows are covered by the TTL alone. The web table row actions (aprovar/pendência for coordenador, SEI toggle for admin) reuse these same PATCH routes keyed on `atendimentoId` — no manual-specific endpoints exist. Full plan: [docs/plans/atendimentos-manuais-validation-actions-and-caching.md](plans/archive/atendimentos-manuais-validation-actions-and-caching.md).

## Find Demeter atendimento

- GET /atendimento/com-relatorio-demeter/:atendimentoId — web-only single Demeter atendimento by id, returning **one** row in the same shape as an item of the `com-relatorio-manual` list (produtor/propriedade/usuario collapsed, `arquivos[]`, município/regional enriched via `getMunicipiosEmater`). This is the fast lookup behind the "Relatórios Demeter" search box: the frontend does one call here instead of walking the paginated list client-side. Sourced from gateway GraphQL `atendimentoComRelatorioManual(id)` (single-id counterpart of `atendimentosComRelatorioManual`, same Demeter filter `link_pdf IS NULL` + indicador 4550 — a non-Demeter id resolves to null upstream). Declared **above** `@Get(':id')` so the 2-segment path isn't shadowed. Authorization is visibility-only (a plain read), via `user.hasAccessTo(AtendimentoService.getAtendimentoAuthScope(atendimentoId))` → **404** (not 403) when out of scope so an id's existence isn't confirmed; **404** too when the id isn't a Demeter atendimento. Uncached (one fast indexed upstream lookup per search); no cache to bust. Stays additive to the mobile contract.

## View public manual PDF

- GET /relatorios/manual?id=<base64urlToken> — web-only public/no-auth PDF view for a manual relatório. Backend user filtering happens before this, in the manual-relatório list. The `id` query param is an obfuscated public PDF token, not an auth token: frontend prepends 5 random decimal digits to the Demeter `atendimentoId`, base64url-encodes that value, and the backend decodes it, strips the 5-digit noise prefix, validates the remaining atendimento id, then builds the PDF. This is only friction against obvious browser-bar ID guessing, not access control. Serves the **combined manual PDF** (Phase 2 of [docs/plans/atendimentos-manuais-file-download-options.md](plans/archive/atendimentos-manuais-file-download-options.md)): the wkhtmltopdf perfil cover, then every stored relatório PDF's pages copied in, then every proof-of-visit photo as an A4 image page — both file groups ordered lowest `idArquivo` first. Assembly lives in [demeter-pdf-assembler.ts](../src/@pdf-gen/demeter-pdf-assembler.ts) (`@cantoo/pdf-lib` for page copy/embed; `sharp` re-encodes photos, normalizing GIF→PNG and applying EXIF auto-orientation). Files come in one call via `AtendimentoService.getArquivosAtendimento` → gateway `GET /api/getArquivosAtendimento` (all active `at_arquivo` rows with binaries, id asc — additive route on the emater server; the single-file `GET /api/getArquivos` stays untouched for the raw-download path). Any stored MIME outside the PNAE-supported set (notably `application/msword`) → **400** clear unsupported-file error before any PDF work; a parse/embed failure on a valid-typed file → **500** naming the offending `idArquivo`. Missing perfil or an empty file set still degrades to a minimal cover PDF (with a "nenhum arquivo" note) instead of failing.

## Create ZIP job

- POST /relatorios/zip/create-job — web-only ZIP generation job. Body is `{ userId, atendimentoIds }`: `userId` must be in `ALLOWED_USER_IDS`; `atendimentoIds` are Demeter `at_atendimento` PKs pasted from Excel (numeric strings, deduped preserving paste order, capped at 4,000 unique ids → **400** above the cap). Mobile never called the old `{ from, to }` shape, so the body change is contract-safe. The worker applies the **ZIP eligibility gate** in `resolveZipItems` — a requested id is included **iff** its `at_atendimento` row (from `atendimentoService.findMany`) has `ativo === true` **and** a truthy `data_see` (SEE-approved; note SEE = `data_see`, not DETEC `data_sei`). The gate runs **before** PNAE/Demeter resolution, so an ineligible/unknown id never triggers a produtor fetch or Demeter hydration and never enters `includedAtendimentoIds`. It then resolves each eligible id to a PNAE relatório or a Demeter manual relatório, builds the parent ZIP, and runs the post-ZIP side effects (below) only for the ids that actually produced a PDF, each log-and-continue on failure since the ZIP is already downloadable. Rotation keeps the last **2** ZIPs on disk. Full plan: [docs/plans/zip-eligibility-filter-and-nao-adicionados.md](plans/zip-eligibility-filter-and-nao-adicionados.md) (supersedes the original [docs/plans/zip-generation-by-atendimento-ids.md](plans/archive/zip-generation-by-atendimento-ids.md)).

## List ZIP included atendimentos

- GET /relatorios/zip/atendimentos-incluidos — web-only read of the `zip:atendimentos-incluidos` Redis hash: `{ [finalZipFilename]: atendimentoIds[] }`, the ids actually included in each previously generated ZIP. Written in `persistZipSideEffects` right after the final ZIP lands; **no TTL, no eviction** — entries outlive the last-2-files disk cleanup, so the frontend `/download` page can show which atendimentos were already exported even after the file is gone. Dev and hmg share one Redis, so cross-env entries showing up in dev is expected, not a bug. Under the `/relatorios/zip` auth-bypass prefix (like status/history/download), so it is unauthenticated; it exposes only zip filenames and atendimento ids.

## List ZIP excluded atendimentos

- GET /relatorios/zip/atendimentos-nao-incluidos — web-only sibling read of the `zip:atendimentos-nao-incluidos` Redis hash, same `{ [finalZipFilename]: atendimentoIds[] }` shape and same no-TTL contract as the included hash. Value is `naoAdicionados = requested − includedAtendimentoIds`: one flat bucket unifying every reason an id didn't make the ZIP — **ineligible** (failed the `ativo && data_see` gate), **errored** (PDF/region failure), or **unresolved** (no relatório on either side). Written alongside the included hash in `persistZipSideEffects`, keyed by the same final ZIP filename. Since it is filename-keyed, the two no-ZIP outcomes (all ids ineligible/unresolved → `empty`; all PDFs fail → `failed`) record nothing here — there is no filename to attach to, and the job status carries the outcome instead. `getAtendimentosNaoIncluidos()` mirrors `getAtendimentosIncluidos()` (both delegate to a shared `readAtendimentoIdsHash`). Under the `/relatorios/zip` auth-bypass prefix, so it is unauthenticated. Mobile does not consume it. Full plan: [docs/plans/zip-eligibility-filter-and-nao-adicionados.md](plans/zip-eligibility-filter-and-nao-adicionados.md).
